ISA-L Erasure Code Performance Report

Xeon 6780E (SRF) · Xeon 6992E+C (CWF) · Xeon Platinum 8576C (EMR) · Xeon 6767P (GNR) · isa-l 96be773 + erasure_code/bench · 2026-10-29

Summary

  • Single core: EMR is fastest (8+4, cache-resident, 50 GB/s of effective data), followed by GNR 37, CWF 21 and SRF 13 GB/s. The P-core lead comes mainly from AVX-512 + GFNI. GNR is slower than EMR per core because it runs AVX-512 + GFNI code at only about 3.09 GHz (EMR: 3.79 GHz). CWF is about 55% faster than SRF, almost entirely from higher work per cycle (IPC 2.09 → 2.95); its clock is only 7% higher.
  • Multi-core, data in cache (pure compute): whole-machine effective throughput is GNR 4.7 TB/s (128 cores) > CWF 4.3 TB/s (one socket, 288 cores) > EMR 3.9 TB/s (112 cores) > SRF 0.96 TB/s (72 cores). At full load CWF and EMR hit the package power limit PL1 and drop to 73% and 70% of their single-core frequency, which matches their scaling efficiency of 72% and 70%. GNR and SRF keep their frequency and scale almost linearly.
  • Multi-core, data in memory: all platforms become memory-bandwidth bound. Per socket, effective throughput is CWF 246 GB/s > EMR 179 > GNR 175 > SRF 122 GB/s. Measured memory bandwidth reaches 81% of theoretical on CWF, 74% on EMR, 63% on GNR and 59% on SRF.
  • E-cores generate extra read traffic when writing parity: SRF/CWF move about 2.0 bytes of memory traffic per byte of source data encoded, P-cores only about 1.5 bytes once bandwidth is saturated. The difference is the read-for-ownership (RFO) of each parity cache line before it is written.
  • SMT does not help EC: running 2 processes per physical core on EMR/GNR lowers cache-resident throughput by 2%–6%. With data in memory it helps by 12%–17% only while memory is not yet saturated, and is neutral at full load.
  • Root-cause analysis: section 10; why CWF lowers its frequency under full load: section 11; per-vCPU comparison of E-cores vs P-core hyper-threads: section 12.

Test environment and method

Two environment caveats:
1. SRF (srfsp) has only 36 cores online per socket (one per 4-core L2 module), far fewer than the 144 cores of a 6780E. Whole-machine SRF numbers therefore describe this machine, not a fully populated 6780E; single-core numbers are unaffected.
2. A qemu VM using about 250 GB runs on SRF NUMA node 1, leaving only about 300 MB free there. Processes on socket 1 have to allocate memory from node 0, so the SRF DRAM results for 64/72 cores are no higher than for 36 cores. Use the single-socket (36-core) result for SRF.
  • All data was produced by the same script erasure_code/bench/ec_bench.sh. Raw results are in erasure_code/bench/results/{srfsp,cwf,emr06,gnrsp}.txt; this page embeds them via gen_report_data.py.
  • Throughput metric: except for the decode results in section 4, all throughput in this report is "effective data", i.e. user source data encoded per second = isa-l's native encode bandwidth × k/(k+p). isa-l natively reports encode = (k+p)×chunk/time and decode = (k+e)×chunk/time; raw values are in the result files and the section 1 table.
  • Single-core tests are pinned to CPU 2 with its SMT sibling idle. "Data in cache" uses the erasure_code_perf default chunk = 128 KB ÷ (k+p), rounded down to 64 B, e.g. 10,880 B for 8+4 and 9,344 B for 10+4. "Data in memory" uses a 64 MB chunk in single-core tests (about 1 GB working set, far larger than any L3 here) and a 16 MB chunk in multi-core tests. Each section title states the k+p and chunk used.
  • Multi-core tests: from 1 physical core up to all of them, one independent 8+4 process per core (EMR/GNR also with 2 per core, the second on the SMT sibling), filling the NUMA nodes of socket 0 in CPU-number order before socket 1. The cache workload uses the default chunk (data stays in each core's cache), the dram workload a 16 MB chunk (256 MB per process). The encode benchmark is extended to 8 s and sampled for 3 s starting 5 s after launch:
    • How frequency, memory bandwidth and power are measured is described in the table below.
    • Only encode results are used: when processes are memory bound, the ones that finish first leave more bandwidth for the rest and inflate their decode results.

All metrics are collected by the scripts while the test processes run, from the CPU's own hardware counters and model-specific registers (MSRs), not from external instruments. Root or passwordless sudo is required (system-wide perf counting, turbostat and /dev/cpu/*/msr).

For a given p, effective throughput stays flat or rises slightly as k grows: encoding cost is driven mainly by the number of parity blocks p. The table also lists isa-l's native encode bandwidth for reference.

2. Chunk size (single core, 8+4, effective data)

Each run uses 16 chunk-sized buffers (8 source + 4 parity + 4 decode outputs). EMR/GNR have 2 MB of L2 per core; with a 256 KB chunk the working set is about 4 MB, exceeds L2, and throughput drops to about 50%–55%. SRF/CWF have a 4 MB L2 per module (used by a single core in this test) and degrade much more gently.

3. Cache vs DRAM (single core, effective data; cache chunk = 128 KB ÷ (k+p), DRAM chunk = 64 MB)

With data in memory, single-core throughput depends on how many memory requests one core can keep in flight rather than on compute: CWF is the fastest single core here and the P-core advantage largely disappears.

4. Number of lost blocks vs decode (single core, 8+4, cache-resident, chunk 10,880 B)

Decode work is proportional to the number of lost blocks e, but bandwidth is counted as (k+e), so the reported value rises as e falls.

10. Root-cause analysis

10.1 Single core: microarchitecture × frequency × ISA

  • GFNI is the foundation: on all four machines the default GFNI path is 2.4–3.1× faster than the table-lookup path (vpshufb). Without GFNI, AVX-512 has no advantage over AVX2 (effective data EMR 15.8 vs 16.2, GNR 14.2 vs 15.2 GB/s): the lookup instructions are limited by execution ports, so wider vectors do not process more bytes per cycle.
  • With AVX-512 + GFNI a P-core encodes about 12–13 source bytes per cycle, 1.4–1.6× its own AVX2 + GFNI path (8.1–8.4 bytes), about 2× a CWF E-core (6.3 bytes) and about 3× an SRF E-core (4.5 bytes).
  • GNR is about 25% slower per core than EMR: first frequency — GNR runs AVX-512 + GFNI at only 3.09 GHz (3.29 GHz for its AVX2 path and 3.59 GHz for AVX-512 without GFNI, all below the 3.9 GHz maximum) versus 3.79 GHz on EMR, 18% lower; second IPC — 3.74 on GNR vs 4.09 on EMR for the same instructions, about 9% lower. This GNR frequency does not depend on the number of active cores (about 3.08 GHz on both 1 and 128 cores), so it is a per-instruction-class frequency level rather than a power limit.
  • CWF is about 55% faster than SRF: frequency 3.19 vs 2.99 GHz (+7%), IPC 2.95 vs 2.09 (+41%), with the same instruction count. The Darkmont core has wider vector execution and load/store ports.

10.2 Multi-core compute: scaling is set by the power limit

  • CWF and EMR: at full load package power reaches 552 W (PL1 550 W) and 767 W (2 × PL1 385 W); frequency is pushed down to 73% and 70% of the single-core value, and scaling efficiency is exactly 72% and 70%: all of the throughput loss comes from the lower clock.
  • GNR: AVX-512 + GFNI code is already capped at about 3.09 GHz. At full load it draws 699 W, just reaching 2 × PL1 350 W, loses only 0.5% of frequency and scales at 98%. So GNR is slower than EMR per core but 21% faster per machine.
  • SRF: with only 36 cores per socket online it draws just 162 W per socket at full load, far below PL1 330 W; frequency stays at 2.99 GHz and scaling efficiency is 99%.
  • Energy efficiency (cache-resident, full load, effective data ÷ package power): CWF 7.8 GB/s/W > GNR 6.7 > EMR 5.1 > SRF 3.0 (SRF has only a quarter of its cores enabled, so uncore power is a large share).

10.3 Multi-core memory access: bandwidth, NUMA nodes and RFO

  • How many cores saturate memory: a single P-core already uses more than ten GB/s of memory bandwidth, and about 16 cores saturate one NUMA node on EMR/GNR (about 130 GB/s). A CWF core also achieves high single-core bandwidth, but 32–64 cores are needed to approach one node's limit (about 165 GB/s). SRF reaches its single-socket limit (about 240 GB/s) at about 32 cores.
  • Steps: EMR/GNR/CWF run with SNC, so each socket is split into several NUMA nodes. Processes fill one node before starting the next, giving step-shaped memory-bound curves: bandwidth only doubles when the number of nodes doubles.
  • RFO costs E-cores 33% more traffic: isa-l writes parity with regular stores by default. When the target cache line is not in cache, the core first reads it (RFO) and then writes it, so reads = source data + parity data. SRF/CWF move about 2.0 bytes per source byte at every core count. EMR/GNR are also around 1.8–1.9 at low core counts with spare bandwidth, but drop to about 1.5 near saturation, i.e. reads are only the source data. P-cores evidently skip the read before full-line writes when bandwidth is tight (presumably the SpecI2M mechanism of Intel server P-cores). With the same memory bandwidth, E-cores therefore encode 25% less source data.
  • Bandwidth utilization: CWF reaches 81% of theoretical (12 channels of DDR5-6400), EMR 74%, GNR 63% and SRF 59% (one socket). The lower GNR and SRF values were not root-caused here; Intel MLC with the same read/write mix would show what these two machines can achieve.
  • 4 cores slower than 2 on CWF: every 4 CWF cores share a 4 MB L2 module, and cores 0–3 are in the same module. Four 256 MB streams contend for one L2 and one module interface, and effective throughput falls from 24 to 17.5 GB/s; 8 cores (2 modules) recover to 32 GB/s. On E-core platforms, memory-intensive work should be spread across modules.
  • SRF gets slower with the second socket: see the environment note above — node 1 memory is taken by a VM, so processes on socket 1 can only use node 0 memory.

10.4 Why SMT does not help

  • Data in cache: one thread already saturates the vector execution and load/store ports (EMR IPC 4.1, GNR 3.7). A second thread only shares the same ports and also competes for L1/L2, so total throughput falls by 2%–6%. On GNR the measured frequency is actually higher with SMT (3.29 vs 3.09 GHz), but throughput per cycle drops more, so the total still falls; the reason for this frequency behaviour needs further investigation.
  • Data in memory: a single thread can keep only a limited number of memory requests in flight. At 8–16 cores, before memory saturates, two threads issue twice as many requests and throughput rises by 12%–17%; once the node or machine is saturated both are equal.
  • Conclusion: EC encoding does not need SMT threads. On P-core platforms the SMT siblings can be left to other work, or EC threads can simply be planned per physical core.

10.5 Recommendations

  • Keep the chunk (stripe unit) at 64 KB or below so the k+p blocks stay in L2; this matters most on EMR/GNR.
  • Streaming encode of large data is essentially memory-bandwidth bound. Plan for roughly 120–250 GB/s of effective data per socket and do not reserve many cores for EC: about 16 cores per NUMA node on EMR/GNR and 32–64 on CWF already come close to the limit.
  • On E-core platforms, try isa-l's EC_ALIGNED_ADDR build option: it writes parity with non-temporal stores (vmovntdq), which in theory removes the RFO reads (up to about 25% of traffic). It requires 32/64-byte aligned buffers and keeps the parity out of the cache, so it needs to be measured.

11. CWF per-core sweep: throughput, frequency, power and temperature from 1 to 288 cores

Script erasure_code/bench/freq_sweep.sh, results results/cwf_freq_*.txt and results/cwf_hold.txt.   1. Turbo ratio limits: all-core turbo is lower than single-core turbo by design. This CPU reaches 3.2 GHz only with at most 18 active cores and is limited to 2.9 GHz with 55 or more. In the packed sweep 1–23 cores ran at 3.16–3.19 GHz and from 25 cores at 2.97 GHz (the boundary differs slightly from the table's 18 cores, possibly due to how hardware counts active cores); a cold-start 96-core run gave 2.87 GHz (the 2.9 GHz group). SRF 6780E has 3.0 GHz in every turbo group and stayed at 2.99 GHz from 1 to 72 cores, which is likely where the "no frequency drop at full load" expectation comes from; this CWF SKU's turbo table is not flat.
  2. Power limit PL1 = 550 W: the real limit with all cores active. The AVX2 + GFNI EC code draws a lot of power per core: a cold-start 96-core run at 2.87 GHz already takes 389 W, which extrapolates to about 1,100 W for 288 cores at 2.9 GHz, twice the TDP. With all cores busy, power is therefore held at 550–570 W (PL2 allows short excursions within the sampling window) and frequency falls to 2.33–2.38 GHz, below the 2.5 GHz base frequency. A sustained 60 s full load is stable at 550 W, 2.33 GHz and 98–102 °C with no thermal throttle events, and the thermal status register shows power limiting (L). Even the plain C code reaches 569 W at 288 cores from a cold start, at 2.50 GHz. Base frequency and all-core turbo are specified for the reference workload Intel uses to define TDP; vector-heavy EC encoding draws more power and is outside that guarantee.
  3. TjMax 107 °C: this machine's cooling is insufficient and, once heat-soaked, the temperature limit triggers before the power limit. During the 35-minute packed sweep, the package reached 107 °C already at 41–44 cores (only about 250 W, far below 550 W) and started throttling frequently. Frequency then kept falling as cores were added, down to 1.98 GHz and 492 W at 288 cores — not even using the power budget — and effective throughput was 17% lower than from a cold start (3.65 vs 4.39 TB/s). At the same core count, a cold start (after 90 s idle) at 96 cores ran at 100 °C, 2.87 GHz with no throttling, while the heat-soaked sweep ran at 107 °C, 2.63 GHz with continuous throttling; after the sweep even the plain C code reached 106–107 °C at 18–19 cores. The heatsink of this Intel AvenueCity reference platform heat-soaks under long high-power runs, so the temperature limit acts before the power limit. A production server with cooling designed for the 550 W TDP should only show the first two limits.
  • Core placement also affects temperature: adding cores in CPU-number order concentrates heat in a few compute units; with spread placement 96 cores ran at 91 °C versus 100 °C packed (cold start). In the heat-soaked sweep the average frequency briefly rises again at 237–240 and 263–266 cores, exactly where newly added, still cool compute units can run faster.
  • Impact on throughput: ideal linear scaling (single core × 288) is about 6.0 TB/s of effective data; cold start or spread placement, power limited, gives about 4.3–4.4 TB/s (72%–73%); the heat-soaked, temperature-limited sweep gives 3.65 TB/s (61%).
  • Recommendations: first check this machine's cooling (BIOS fan policy, inlet temperature, heatsink mounting) — reference platforms often default to quiet fan profiles. Spread EC threads across modules and compute units. In real deployments EC is usually memory-bandwidth bound (section 8), so all 288 cores are not needed; fewer cores can run at a higher frequency.

12. Per-vCPU comparison: E-cores vs P-core hyper-threads at 1–4 vCPUs (10+4, effective data)

Clouds usually sell virtual CPUs (vCPUs), and on P-core platforms vCPUs come in hyper-thread pairs: 2 vCPUs are the 2 hyper-threads of one physical core, 3 vCPUs are one full core plus one hyper-thread of the next core, and 4 vCPUs are 2 full physical cores. E-core platforms have no SMT, so n vCPUs are n physical cores (chosen here so that they do not share an L2). One 10+4 process runs on each vCPU and the effective data is summed. The cache-resident case uses the default chunk, the DRAM case a 64 MB chunk (about 1 GB per process). Each case is the best of 3 runs (section 8 of the script).

Findings

  • E-cores scale linearly with vCPUs, P-cores in steps: each additional E-core vCPU is a full core, so cache-resident throughput is exactly linear (CWF 21.4 → 42.8 → 64.1 → 85.8 GB/s). P-core throughput only rises when a new physical core is added; adding the second hyper-thread of a core lowers it by 3%–6% (EMR 52.6 → 49.8 → 102.8 → 99.9 GB/s) because one thread already saturates the vector units.
  • Data in cache: at 1 vCPU the P-cores are far ahead (EMR is 2.5× CWF), but the sibling hyper-thread is idle then, so that vCPU effectively owns a whole physical core. Comparing full pairs: at 4 vCPUs EMR 99.9 > CWF 85.8 > GNR 72.9 > SRF 55.4 GB/s — CWF delivers about 86% of EMR and 18% more than GNR.
  • Data in memory: P-core SMT brings almost nothing (both threads share the memory requests one physical core can keep in flight), while E-cores scale nearly linearly. From 2 vCPUs on CWF leads across the board: at 4 vCPUs CWF 50.4 > SRF 35.4 > GNR 26.1 > EMR 24.6 GB/s — CWF delivers 2.0× EMR and 1.9× GNR, and SRF about 1.4× the P-cores. Even with a single vCPU CWF is 21% ahead of EMR.
  • CWF module sharing: 2 cores in the same L2 module are as fast as 2 separate cores in cache, but reach only 23.2 GB/s in memory (28.9 when separate); the module's shared L2 and its external bandwidth become the bottleneck. Spread vCPUs or pinned threads across modules.
  • Implication: for vector-heavy, streaming workloads like EC, one vCPU of a P-core platform is worth only half a physical core. Priced per vCPU, CWF delivers about 86% of EMR's per-vCPU throughput and more than GNR when data is in cache, and about 2× the P-cores when data is in memory. On GNR the measured frequency is higher with SMT (3.29 vs 3.09 GHz) but throughput per cycle drops more, so the total still falls.
